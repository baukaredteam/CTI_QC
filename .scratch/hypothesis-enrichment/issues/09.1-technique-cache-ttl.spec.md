# Spec: 09.1 — Technique cache TTL hardening

**Parent:** Ticket 09 `c26b6e6` (resolved HEAD of this run)
**Status:** ready-for-agent
**Type:** task

## Problem

`ThreadlinqsCache` keeps one TTL (`ttl_hours`, default 24) applied to every
entry, including technique entries. Ticket 09's `enrich_predictions` calls
`put_technique(technique_id, envelope)` with no separate technique TTL, so in
production construction (`ThreadlinqsCache(redis)`) techniques expire after
24 hours while the documented contract (Ticket 09 acceptance, spec HC-2)
requires 7 days. The existing unit test hides this by passing
`ttl_hours=enricher.TECHNIQUE_CACHE_TTL_HOURS` explicitly — a test-only
override that never matches the production call site.

## Exact acceptance contract

- [ ] Bundle cache default TTL remains 24 hours.
- [ ] Technique cache default TTL becomes 7 days (`7 * 24` hours).
- [ ] Technique key remains `tl:technique:<sha256(technique_id)>`.
- [ ] Bundle key remains `tl:bundle:<sha256(bundle_id)>` (unchanged).
- [ ] Cache hit performs no MCP call.
- [ ] Cache miss performs one MCP call and one cache put.
- [ ] Ticket 09 projection, batch size 20 and timeout 5 seconds remain
      unchanged.
- [ ] No `scan_feed` wiring in Ticket 09.1.
- [ ] No frontend changes.
- [ ] No real MCP/network in tests (FakeThreadlinqsClient / fake redis only).

## Implementation contract (minimal, additive)

```python
DEFAULT_CACHE_TTL_HOURS = 24
DEFAULT_TECHNIQUE_CACHE_TTL_HOURS = 7 * 24

class ThreadlinqsCache:
    def __init__(
        self,
        redis,
        ttl_hours: int = DEFAULT_CACHE_TTL_HOURS,
        technique_ttl_hours: int = DEFAULT_TECHNIQUE_CACHE_TTL_HOURS,
    ):
        self._ttl_seconds = ttl_hours * 3600
        self._technique_ttl_seconds = technique_ttl_hours * 3600
```

- Old positional `ttl_hours` constructor behavior stays compatible.
- New parameter is added **after** `ttl_hours` (keyword-optional).
- `put` (bundle) keeps using `_ttl_seconds` (24h default).
- `put_technique` uses `_technique_ttl_seconds` (7-day default).
- `get`, `put`, `has`, `invalidate` bundle semantics unchanged.
- `get_technique` behavior unchanged.
- `enrich_predictions` does not pass unknown kwargs into the old API; the new
  default applies at the cache constructor, not at the call site.
- No global state added.
- Ticket 09 projection / batching / timeout unchanged.

**Do NOT** fix this by changing the existing `ttl_hours` default from 24 to
168 — that would break the bundle cache contract. Two independent TTLs are
required.

## Test contract

New file `backend/tests/unit/test_threadlinqs_cache.py` plus an edit to the
existing Ticket 09 test `test_cache_miss_calls_then_puts_with_seven_day_ttl`
in `backend/tests/unit/test_mcp_enricher.py`, which must construct
`ThreadlinqsCache(redis)` (production default) instead of
`ThreadlinqsCache(redis, ttl_hours=enricher.TECHNIQUE_CACHE_TTL_HOURS)`.

Minimum assertion-level tests (must fail RED at assertion level, not at
import/collection, against pre-fix code):

1. `ThreadlinqsCache(redis)` default `put_technique` writes `ex == 7 * 24 * 3600`.
2. `ThreadlinqsCache(redis)` default bundle `put` writes `ex == 24 * 3600`.
3. Custom `ttl_hours=12` changes bundle TTL to `12 * 3600`.
4. Custom `technique_ttl_hours=48` changes technique TTL to `48 * 3600`.
5. Custom bundle and technique TTLs can differ in one instance.
6. Technique key stays `tl:technique:<sha256(technique_id)>`.
7. Bundle key stays `tl:bundle:<sha256(bundle_id)>`.
8. Malformed Redis JSON entry returns `None` and follows existing safe
   deletion behavior.
9. Production-style `ThreadlinqsCache(redis)` passed to `enrich_predictions`
   causes cache miss -> one MCP call + put with 7-day TTL.
10. Cache hit performs no MCP call.
11. Existing Ticket 09 `attack_flow` projection unchanged.
12. Existing Ticket 08 fields unchanged (no regression).

Verification commands (targeted, then full):
